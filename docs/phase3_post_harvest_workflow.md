# Phase3 Post-Harvest Workflow

> Historical/provider workflow. Current active Phase 3 runtime supports only
> `soft-pack` and `soft-apply`; use this only when auditing or manually
> reconstructing old Aristotle harvest work.

## Purpose

This is the operator runbook for local repair after Aristotle harvest.

Use it when:

- Aristotle produced a raw Lean file
- local phase3 verification did not promote it
- phase4 remains disabled

The workflow is intentionally aligned with `phase2` prompt-pack:

- the repository prepares a repair pack
- Codex is the primary repair agent
- verification remains the acceptance gate

## Core Distinction

Not every failed harvest should enter proof repair.

There are three failure classes:

1. `proof_incomplete`
2. `statement_drift`
3. `harvest_missing_clean_file`

Only `proof_incomplete` should go directly into proof repair.

## CLI Modes

```powershell
python .\run_chapter.py --phase 3 --phase3-mode repair-pack --tasks <task_id>
python .\run_chapter.py --phase 3 --phase3-mode repair-verify --tasks <task_id>
python .\run_chapter.py --phase 3 --phase3-mode repair-verify --tasks <task_id> --candidate <path>
```

Rules:

- `repair-pack` requires exactly one task id
- `repair-verify` requires exactly one task id
- `repair-verify` defaults to `phase3_post_harvest_packs/<task_id>/draft.lean`
- `--candidate` is only for verifying an external Lean file; the repo still snapshots it into `candidate_vN.lean`

## Directory Layout

Each task gets a directory:

- `phase3_post_harvest_packs/<task_id>/`

Main files:

- `task.json`
- `metadata.json`
- `operator_prompt.md`
- `context.md`
- `raw_candidate.lean`
- `draft.lean`
- `attempt_history.json`
- `failure_summary.md`
- `build_feedback.txt`
- `verification_report.md`
- `candidate_v1.lean`, `candidate_v2.lean`, ...
- `verify_result_v1.json`, `verify_result_v2.json`, ...

## Artifact Roles

### `raw_candidate.lean`

Exact Aristotle baseline. Do not edit this file.

### `draft.lean`

Live repair working file. Edit this file.

### `context.md`

This is the high-value orientation file. It contains:

- original plan statement
- staged theorem header
- raw theorem header
- failure classification
- hard dependencies
- soft imports
- final import union
- raw file path
- verification log path
- Aristotle summary path

### `build_feedback.txt`

Latest local verification failure details. Read this before the next repair attempt.

### `failure_summary.md`

Condensed iteration memory. If the same failure repeats, it will tell you to stop patching and rewrite cleanly.

## Standard Procedure

### Step 1: Audit the failure type

Run:

```powershell
python .\run_chapter.py --phase 3 --phase3-mode repair-pack --tasks <task_id>
```

Then inspect:

1. `context.md`
2. `failure_summary.md`
3. `raw_candidate.lean`
4. the referenced verification log
5. the referenced Aristotle summary

Interpretation:

- if staged header and raw header match: `proof_incomplete`
- if raw header changed relative to staged header: `statement_drift`
- if raw file is missing or still contains `sorry`: `harvest_missing_clean_file`

### Step 2: Decide whether proof repair is allowed

Allowed:

- `proof_incomplete`

Blocked from ordinary proof repair:

- `statement_drift`
- `harvest_missing_clean_file`

If blocked, do not push the task through `repair-verify` as if it were a routine proof bug.

### Step 3: Edit `draft.lean`

For `proof_incomplete`:

- preserve the theorem or definition statement
- repair only the body
- do not edit dependency files
- prefer the smallest proof change that closes the local build

### Step 4: Verify

```powershell
python .\run_chapter.py --phase 3 --phase3-mode repair-verify --tasks <task_id>
```

Or:

```powershell
python .\run_chapter.py --phase 3 --phase3-mode repair-verify --tasks <task_id> --candidate <path>
```

What `repair-verify` does:

1. snapshots the candidate into `candidate_vN.lean`
2. checks for a real top-level declaration
3. runs REPL validation
4. runs temporary `lake build`
5. if that passes, promotes to active outputs
6. runs final `lake build ToyApollo.Output.<task_id>`
7. writes `verify_result_vN.json`
8. updates `attempt_history.json`, `failure_summary.md`, `verification_report.md`, and the ledger

## Statement Reconciliation Cases

### `prob_4_8`

This is the reference `proof_incomplete` case.

- the staged statement and raw statement match
- Aristotle chose a mathematically reasonable route
- local proof details did not close

This is a normal repair-pack candidate.

### `prob_4_11`

This is the reference `statement_drift` case.

- the package sent to Aristotle matched the textbook statement
- Aristotle changed the theorem by adding boundedness
- the change was motivated by `Filter.limsup` semantics on `ℝ`

This is not a normal proof-repair task.

It requires statement reconciliation first.

## Limsup/Liminf Policy

For chapter-local sequence limsup/liminf problems, prefer textbook semantics:

- `seqLimsup`
- `seqLiminf`
- or equivalent tail `sup` / `inf` formulations

Do not default to `Filter.limsup a atTop` on `ℝ` unless the task explicitly asks for filter-theoretic limsup.

This policy exists because textbook intent and `Filter.limsup` on `ℝ` can diverge.

## Promotion Rules

A post-harvest repair is promoted only if:

1. the task is not blocked by `statement_drift`
2. the candidate has a real top-level declaration
3. REPL validation succeeds
4. temporary `lake build` succeeds
5. final `lake build ToyApollo.Output.<task_id>` succeeds

If verification fails:

- active outputs remain untouched or are restored
- the candidate snapshot remains on disk
- the verify result remains on disk
- the ledger remains in a non-completed state

## Relationship to Phase2

This workflow is intentionally phase2-shaped.

Common structure:

- pack first
- edit `draft.lean`
- append-only candidate snapshots
- append-only verify results
- local verification as the promotion gate

Main difference:

- `phase2` starts from a local task pack
- post-harvest repair starts from Aristotle raw output plus phase3 verification artifacts
